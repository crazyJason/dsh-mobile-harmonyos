# 真机测试计划

本文是 HarmonyOS NEXT 真机手工测试计划，覆盖配对、浏览、证书、网络与生命周期场景，并规定缺陷报告需要采集的信息。

> 🟡 **执行状态：主流程、失败路径与扫码入口已执行（2026-11-24 五轮真机）**
>
> - **L1 已执行**：TC-01（安装/启动/空状态）、TC-02（设备端协议自检）在真机上通过；自检项数随构建增长，**当前构建为 33 项**（首轮 24 项）。
> - **L2 已执行（局域网主流程）**：装好电脑端 `dsh-mobile@0.8.15` 后，局域网配对（`dsh2` 密钥 + CA 固定）、ArkWeb 登录浏览、进程重启后恢复、电脑端设备列表全部通过。
> - **L3 已执行（失败路径）**：错误/重复/过期配对码、撤销设备、来源地址变化、网关不可达、非法输入、证书不匹配、局域网无 `ca.cer` 全部通过；**未执行**：设备上限（TC-13）、受信网段的网关侧策略（TC-15 客户端侧已验证）。
> - **L4 已执行**：Wi-Fi↔移动网络切换、前后台切换、重启恢复、会话丢失后重新续期（不需重新配对）。
> - 三轮共发现并修复 7 个**只有真机才能暴露**的缺陷（见 [§11.3](#113-本轮缺陷已修复)：全角加号字形、底部导航条白条、系统弹窗浅色、启动日志不可见、CA 基本约束误拒、撤销归类与文案、TLS 错误码错判）。
> - **仍未执行**：设备上限、受信网段的网关侧策略、命名隧道与自签 FRP 远程入口（TC-16/17）、ArkWeb Cookie 属性检查（TC-31）。公网证书**快速隧道**入口的 TC-16B 已于 2026-11-24 第四轮通过（手机仅蜂窝、经 Cloudflare 隧道配对并加载 DSH 主页），见 [§11.6](#116-2026-11-24-第四轮cloudflared-快速隧道远程通道tc-16b)。
> - ✅ **扫码配对已端到端验证（2026-11-24 第五轮）**：「扫一扫二维码」拉起**系统 Scan Kit 默认界面**（无相机权限弹窗，带手电筒/图库入口）；扫局域网二维码走 CA 固定、扫远程二维码走系统信任库，两条都直接配对成功并在列表可见；取消路径无错误文案；自检 33 项（含 3 条扫码头）全过。见 [§11.7](#117-2026-11-24-第五轮扫码通道接入tc-32tc-34)。

## 0. 测试前置条件

### 0.1 设备与环境

| 项目 | 要求 |
| --- | --- |
| 手机 | 真实 HarmonyOS NEXT 设备（模拟器不能替代：ArkWeb、Asset Store、网络权限行为需真机） |
| 系统 | HarmonyOS NEXT 正式版；记录具体版本与 ArkWeb 版本 |
| 安装包 | 用 DevEco Studio 自动签名后的 HAP；未签名包无法安装 |
| 电脑 | 已安装 DeepSeek Harness 并启用 `dsh-mobile` 插件，移动访问已开启 |
| 网络 | 手机与电脑在同一 Wi-Fi（局域网场景）；远程场景另备自签名 FRP 或公网隧道入口 |
| 电脑端工具 | 能查看插件版本、设备列表、撤销设备、重新生成配对码；能看到网关日志 |
| 手机端工具 | `hdc`（抓日志）、录屏/截图工具 |

### 0.2 版本记录

每轮测试开始前记录以下版本，写入测试报告：

- 手机型号与 HarmonyOS 版本；
- ArkWeb 版本（系统应用信息或浏览器内核信息中可见）；
- DSH 版本；
- `dsh-mobile` 插件版本（电脑端插件页面或 `package.json`）；
- 本仓库构建信息（构建日期、git commit、是否签名）；
- 入口类型（局域网 / 自签名 FRP / 公网隧道）与端口。

### 0.3 每次用例前的准备

1. 用 `hdc install -r` 安装最新签名 HAP；
2. 在电脑端为每个“配对”用例**重新生成**配对链接（token 一次性，不能复用）；
3. 清空日志：`hdc shell hilog -r`；
4. 若用例涉及“已配对状态”，先确认 App 设备列表中的记录状态与预期一致。

### TC-01 安装与首次启动

| 项 | 内容 |
| --- | --- |
| 前置 | 已签名 HAP；手机无旧版本 |

### TC-02 设备端协议自检（安装后的首个冒烟检查）

| 项 | 内容 |
| --- | --- |
| 前置 | TC-01 通过 |
| 步骤 | 1) 展开空状态；2) 点击「运行协议自检」 |
| 预期 | 弹窗显示「协议自检通过」，并说明 N 项检查全部通过（origin 解析、拒绝 HTTP/路径/query/userinfo、默认端口、同源、`wss:` 固定 authority、`dsh1`/`dsh2` 密钥、配对链接、legacy 片段、ASN.1 证书有效期解析等） |

## 3. 用例：局域网配对

### TC-04 局域网配对（粘贴 legacy 链接）

| 项 | 内容 |
| --- | --- |
| 前置 | 手机与电脑同一 Wi-Fi；插件已开启移动访问；App 无该电脑记录 |
| 步骤 | 1) 电脑端生成配对链接/二维码；2) 把完整链接复制到手机剪贴板（聊天工具发送后复制）；3) App「添加电脑」→「从剪贴板粘贴」；4) 确认 host/port（可再点「扫描局域网」选中同一台电脑）；5) 点击「开始配对」 |
| 预期 | 配对成功提示；列表出现该电脑，显示名称、`host:port`、局域网标签与可达状态；配对过程中不出现证书错误 |
| 证据 | 添加页与列表截图、电脑端设备列表新增记录、hilog（不得包含 token） |
| 备注 | 局域网入口的链接常见为 `#instance=<64hex>&token=<43char>`，也可能是 `dsh2` 自签入口；两种都应按本文预期成功 |

### TC-05 局域网配对（dsh2 自签链接）

| 项 | 内容 |
| --- | --- |
| 前置 | 电脑端使用自签 CA 入口（例如自签名 FRP 或非 discovery 模式），配对链接形如 `#key=dsh2.<64hex>.<43char>` |
| 步骤 | 同 TC-04 |
| 预期 | 成功；App 从 `/mobile-access/ca.cer` 下载 CA，校验证书指纹后固定；后续浏览无证书告警 |
| 证据 | 截图、hilog、电脑端插件日志中的 `ca.cer` 请求 |

### TC-06 局域网扫描发现

| 项 | 内容 |
| --- | --- |
| 前置 | 同一 Wi-Fi；电脑网关运行中 |
| 步骤 | 1) 进入「添加电脑」；2) 点「扫描局域网」；3) 观察结果列表 |
| 预期 | 数秒内列出运行中的电脑（`deviceName` + host:port）；同一台电脑只出现一次；点选后自动填入地址；若网络隔离/防火墙拦截，列表为空并给出“未发现电脑”提示 |
| 证据 | 扫描结果截图、电脑端防火墙设置 |
| 备注 | UDP 3443 与 mDNS 可能被路由器 AP 隔离/防火墙拦截；扫描失败不阻塞“粘贴链接”路径 |

### TC-07 手动填写地址配对（裸密钥）

| 项 | 内容 |
| --- | --- |
| 前置 | 粘贴的输入是裸 `dsh2` 密钥（不含 origin） |
| 步骤 | 1) 粘贴密钥；2) 在「手动填写」里输入 `192.168.x.x:3443`；3) 配对 |
| 预期 | 成功；列表展示手填地址与配对得到的电脑名称（未扫描到时显示 host）。`dsh1` 裸密钥（公网证书入口）走同一路径，见 TC-16 |
| 补充 | 同一字段也验证缺省端口规则：只写 `192.168.x.x` 应补 `3443`；写 `192.168.x.x:443` 应原样保留 443（不回到 3443） |
| 证据 | 截图 |

### TC-07B 裸密钥与所选电脑不匹配

| 步骤 | 1) 粘贴 A 的裸密钥；2) 扫描局域网并选中电脑 B；3) 点「开始配对」 |

| 证据 | 截图、B 端网络日志（应无 native-pair 请求） |

### TC-08 无局域网但粘贴完整链接

| --- | --- |
| 前置 | 手机使用移动网络，电脑位于公网可达入口（公网证书或自签名均需可达） |
| 步骤 | 粘贴完整配对链接并配对 |
| 预期 | 由链接决定 origin；bootstrap 超时按远程档位（数秒）生效；成功或给出明确的网络/证书错误 |
| 证据 | 截图、hilog、电脑端访问日志 |

### TC-32 扫码配对（局域网二维码）

| 项 | 内容 |
| --- | --- |
| 前置 | 手机与电脑同一 Wi-Fi；电脑端「移动访问」已开启并点开「生成配对二维码」，二维码留在电脑屏幕上；App 内无该电脑记录 |
| 步骤 | 1) App「添加电脑」→ 点「扫一扫二维码」；2) 系统扫码界面出现后，把手机对准电脑屏幕上的二维码；3) 识别成功后不要离开页面，等待配对完成 |
| 预期 | 扫码界面自动关闭回到 App，输入框里出现与二维码一致的链接；**直接开始配对，不需要再点「开始配对」**；成功后回到列表并出现该电脑（名称、`host:port`、局域网标签、可达状态）；全程不出现相机权限弹窗 |
| 证据 | 扫码界面与配对成功截图、电脑端设备列表新增记录、`hilog -T DshMobile`（只应有 `pairing QR scanned`，**不得**出现链接原文或 token） |
| 备注 | 二维码有效期与配对码一致（默认 120 秒），电脑端生成后要尽快扫；扫码界面是**系统**界面，返回键/侧滑返回等于取消；扫到的完整链接与粘贴的完全等价（[ADR-0006](adr/0006-scan-with-system-scankit-ui.md)） |

### TC-33 扫码配对（远程通道二维码）

| 项 | 内容 |
| --- | --- |
| 前置 | 手机只开移动数据、`wlan0` 无地址；电脑端配置公网证书入口（例如 cloudflared 快速隧道），并在**远程通道**生成配对二维码 |
| 步骤 | 同 TC-32，扫的是远程通道的二维码 |
| 预期 | 与 TC-16B 一致：`ca.cer` 404 → 平台信任库 → 配对成功；列表出现远程记录（远程标签）；因为 origin 是隧道主机名，缺省端口必须是 443（不是 3443） |
| 证据 | 截图、电脑端 `mobile-access/remote/devices.json` 新增记录 |
| 备注 | 必须用**远程通道**的二维码：管理接口按通道分开（`/api/mobile-access/remote/pairing/open`），用局域网二维码在公网入口上配对必然 401（见 [§11.6](#116-2026-11-24-第四轮cloudflared-快速隧道远程通道tc-16b)） |

### TC-34 扫码的边界：取消 / 非配对码 / 裸密钥二维码

| 项 | 内容 |
| --- | --- |
| 前置 | 准备三种二维码：① 配对二维码；② 任意无关二维码（例如一条普通网址）；③ 只含裸 `dsh1` 密钥的二维码 |
| 步骤 | 1) 点「扫一扫二维码」后立刻按返回键或侧滑取消；2) 扫 ②；3) 扫 ③；4) （可选）在没有 HMS Scan 服务的设备上重复步骤 1 |
| 预期 | 1) 只回到 App，**不显示错误文案、不弹 toast**，输入框内容不变；2) 提示无法识别（「无法识别的配对信息，请粘贴完整的配对链接」或「链接里没有有效的配对密钥，请在电脑端重新生成配对链接」），不发起任何网络请求；3) 输入框填入密钥并提示「二维码里只有配对密钥，请再选择电脑或填写地址」，补地址后才开始配对；4) 提示「扫码没有成功，请改用「从剪贴板粘贴」」，粘贴路径仍然可用 |
| 证据 | 三次操作截图、hilog（取消只应出现 `scan cancelled by the user`） |

### TC-12 电脑端撤销设备

| 项 | 内容 |
| --- | --- |

## 9. 缺陷报告需要采集的信息

一个可处理的缺陷报告应包含：

| 字段 | 说明 |
| --- | --- |
| 用例编号 | 例如 TC-04、TC-21 |
| 严重级别 | 阻断 / 严重 / 一般 / 轻微 |
| 手机型号 | 完整型号（如 `Pura 70 Pro`） |
| HarmonyOS 版本 | 设置 → 关于手机 → 版本号（示例：`HarmonyOS NEXT x.y.z`） |
| ArkWeb 版本 | 系统应用信息或浏览器内核信息中的版本号 |
| DSH 版本 | 电脑端 DeepSeek Harness 版本 |
| dsh-mobile 插件版本 | 电脑端插件版本（与 `metadata.pluginVersion` 对照） |
| 本仓库构建 | git commit、构建日期、是否签名、构建命令来源 |
| 入口模式 | 局域网 / 自签名 FRP / 公网隧道 / 反向代理 |
| 网络拓扑 | 手机网络、电脑网络、是否有 AP 隔离/代理/VPN |
| 复现步骤 | 逐步操作，含输入类型（不要贴真实 token） |
| 实际结果 | 现象、错误文案、截图/录屏 |
| 预期结果 | 对应本文用例的预期 |
| 发生时间 | 精确到分钟，便于对齐日志 |
| 日志 | `hdc shell hilog -T DshMobile` 的输出，**脱敏后**提供 |
| 电脑端证据 | 插件设备列表、网关日志中的对应请求（状态码） |

### 9.1 必须先脱敏的内容

- 配对链接的 fragment（包含一次性 token）；
- `deviceToken`、`sessionToken`、`csrfToken` 的完整值（保留前 2–4 位与长度即可）；
- 公网域名/IP（如涉及隐私，用 `x.x.x.x`/`example.com` 替代）；
- 用户数据、会话内容、文件路径；
- 签名材料：`*.p7b`、`*.p12`、`*.cer`、`*.pem` 及其密码，**永远不要**附在缺陷里。

### 9.2 日志抓取

```powershell
# 清空旧日志
& 'D:\Programs\Huawei\DevEcoStudio\sdk\default\openharmony\toolchains\hdc.exe' shell hilog -r

# 只抓本项目（tag = DshMobile，domain = 0x0D5B）
& 'D:\Programs\Huawei\DevEcoStudio\sdk\default\openharmony\toolchains\hdc.exe' shell hilog -T DshMobile -x
```

> `-x`（非阻塞读，打印完缓冲区即退出）**必须带**。不带 `-x` 时 `hilog -T DshMobile` 会一直流式输出不退出，
> 在脚本或 CI 里会把命令挂死；要实时看日志再手动去掉 `-x`。
>
> 另外：日志 domain 必须是 `0x0D5B`。用 `0x0000` 打日志在 HarmonyOS 7 上**看不到**（第一轮真机踩过，
> 见 [§11.3](#113-本轮缺陷已修复) D-04），所以 ability 层也必须走 `common/Log.ets` 而不是直接调 `hilog`。

### 11.3 本轮缺陷（已修复）

七个缺陷都是**只有真机才能暴露**的，模拟器和编译期都发现不了：

| 编号 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| D-01 | 右上角「添加」按钮里的加号显示成一个白色小方块 | 源码用的是全角加号 `U+FF0B`，设备字体栈里没有该字形，回退渲染成小方块 | 改用 ASCII `+`，字号 20 → 24（`pages/Index.ets`） |
| D-02 | 底部导航条区域是一条**白条**，与深色界面割裂 | 该区域实际绘制的是**窗口背景**，只设 `setWindowSystemBarProperties({ navigationBarColor })` 不够（该调用本身成功、无报错） | `loadContent` 后补 `setWindowBackgroundColor('#0B0E14')`（`entryability/EntryAbility.ets`） |
| D-03 | 协议自检弹窗、toast 是浅色主题，浮在深色界面上很突兀 | 应用界面固定深色，但没有声明色彩模式，系统组件仍按设备主题（浅色）绘制 | `onCreate` 中 `setColorMode(COLOR_MODE_DARK)`（`entryability/EntryAbility.ets`） |
| D-04 | `hilog -T DshMobile` 一条应用日志都收不到 | ability 层直接调用 `hilog.info(0x0000, ...)`；domain `0x0000` 的日志在 HarmonyOS 7 上被丢弃，启动/窗口错误日志全部丢失（`system bar styling unavailable` 这类告警也看不到） | 改走 `common/Log.ets`（domain `0x0D5B` + 脱敏），并给 `Log` 增加 ability 层用法（`entryability/EntryAbility.ets`） |
| D-05 | **所有**局域网配对失败，提示「证书校验失败：网关证书与配对信息不一致」 | `X509Cert.getBasicConstraints()` 返回的是**路径长度**，HarmonyOS 对「CA:TRUE 且省略 pathLenConstraint」的证书返回 `-1`；代码把 `< 0` 当作“不是 CA”直接拒绝，而 `dsh-mobile` 生成的配对 CA 恰好没有该可选字段。真机日志：`pairing CA: basicConstraints=-1 … withinValidity=true` → `basic constraints do not allow the CA role` | 不再拿基本约束当门禁：保留「指纹 == instanceId + 有效期 + 自签名验签」，仅记录该值供排障（`protocol/CertPin.ets`，说明见 [ARCHITECTURE §9.2](ARCHITECTURE.md#92-bootstrap-链路)） |
| D-06 | 撤销设备后卡片显示「配对已过期」，打开时提示「配对码已失效或已被使用」——用户明明没在用配对码 | 插件撤销设备时**删除**记录，`native-probe` 只回 `401 authentication_failed`，客户端无法区分“被撤销”和“凭据失效”；同时打开设备仍先发网络请求 | 会话场景改用专门文案「这台电脑已不再信任本设备（可能已在电脑端移除），请重新配对」；`openDevice` 对 `REVOKED`/`EXPIRED` 直接本地拒绝（`service/AppService.ets`、`pages/Index.ets`、`pages/BrowserView.ets`），[PROTOCOL](PROTOCOL.md#105-失败分类) 记录该插件行为 |
| D-07 | 网关关掉时提示「证书校验失败：网关证书与配对信息不一致」，把“连不上”说成“证书不对” | 归类表把 `2303501`（SSL is null，端口不可达时代码）当成握手失败，却漏掉真正的证书校验失败 `2303504` | 按 SDK 语义重分类：`2303504`/`2303505` → TLS，`2303501`/`2303502`/`2303503` → NETWORK（`protocol/TlsHttp.ets`），真机复验关网关后显示「无法连接电脑，请检查网络与移动访问开关」 |

**由此顺带补的可诊断性**：TLS 失败原先只折叠成一句用户提示，没有任何设备端日志。现在 `TlsHttp.ets` 会记录 socket 错误码，
`AppService.pair` 会记录「CA 是否取到 / 是否匹配 / 最终失败类别」，`CertPin.validatePairingCa` 会记录基本约束与有效期判定——
D-05 就是靠这三条日志在真机上一轮定位的。

**本轮新增的两个坑（都表现为「配对码已失效或已被使用」）**：

1. **配对码默认只活 120 秒**（插件 `pairingTtlMs`，可配 10–600 秒）。远程场景要先关 Wi-Fi、切 App、粘贴，很容易超出窗口；码一过期网关回 401，客户端把它映射成「配对码已失效或已被使用」，看起来像客户端缺陷。**面板显示的有效期必须当真：生成后立刻粘贴。**
2. **管理接口按通道分开**：`POST /api/mobile-access/pairing/open` 作用于**当前活动**网关（本次是局域网入口），它生成的码在公网入口一定 401；远程通道要用 `POST /api/mobile-access/remote/pairing/open`（局域网对应 `/api/mobile-access/lan/...`）。自动化脚本拿错通道会稳定复现“码失效”。

**复现最短路径**（本轮已脚本化）：`/api/mobile-access/remote/pairing/open` 取响应里的 `appPairUrl` → 手机 `uitest uiInput text` 填链接 → 点「开始配对」→ 服务端 `remote/devices.json` 计数 +1 即成功。

**结论**：客户端远程路径（公网证书 → 系统信任库 → 远程记录 → ArkWeb 浏览）**首次端到端跑通**；`preserveRemotePin`（TC-18B 的端到端部分）仍需要一次“远程已固定 CA 后再用 dsh1 密钥配对”的实验，本轮未做。

**本轮新增的两个坑**：

1. **`uitest uiInput text` 传整条链接必须给设备端 shell 加单引号。** 链接里的 `&token=…` 会被 `/bin/sh` 当成后台操作符：`hdc shell uitest uiInput text $url` 只把 `#instance=…` 送进输入框，配对必然失败（表现为「无法识别的配对信息」）。正确写法是 `hdc shell "uitest uiInput text '$url'"`。
2. **配对码「一次性 + 120 秒」在扫码场景下更容易踩。** 同一个二维码扫第二次必定 401；面板重新生成二维码会立刻让旧码失效。所以「先生成码、再折腾 UI、最后扫」的顺序很容易超时，自动化取证时要么先扫后取证，要么把 `pairingTtlMs` 调大（属电脑端配置）。

**取证命令（新增）**：`hdc shell bm clean -n <bundle> -d` 清应用数据回到空列表（跑 TC-02 用，会让本地记录全丢）；`hdc shell uitest uiInput keyEvent Back` 取消系统扫码界面；`hdc shell hilog -T DshMobile -x` 确认只出现 `pairing QR scanned` / `scan cancelled by the user`，**没有链接原文或 token**。

**相机这一步是怎么自动化掉的**：扫码界面本身可以用 `uitest uiInput click` 拉起，剩下的只是「让取景框里有二维码」。做法是把插件 `pairing/open` 返回的 `qrSvg` 写进一个本地 HTML（白底、64vmin、顶部留白避开任务栏悬浮窗），用默认浏览器打开，然后从 hdc 注入点击「扫一扫二维码」；只要手机仍对着屏幕，9 秒内就会自动解码、自动配对、回到列表。这条路径比手点更稳，因为省掉了「人看一眼再按」的时间，配对码 120 秒的窗口不再紧张。

**一个未解释的现象**：22:23 那次局域网扫码之后，列表里只剩局域网记录，先前 22:19 配对的远程记录不见了；随后两次「force-stop + start」都稳定保留两条记录，重配远程后再重启也正常，未能复现。当时手机正被人工操作，最可能是手动删除了该卡片；若后续再出现「记录无故消失」，按「`bm clean` / 手动删除 / `DeviceStore.save` 未 flush」三个方向查，本条留作线索。

**结论**：扫码通道端到端跑通——局域网（CA 固定）与远程（系统信任库）两条入口都能从二维码直接完成配对，取消与非配对码路径也有覆盖；TC-32、TC-33、TC-34 均为 PASS。
